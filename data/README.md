# データ層（back）の説明

アプリ（`index.html` / `節別予想.html`）が使うデータは、すべてここから生成されています。
**HTML を直接手で書き換えないでください。** データを直したいときは、このディレクトリと
`tools/` を触って `node tools/build.js` を実行します。

---

## 1. 取得元

**Ｊリーグ公式データサイト** `https://data.j-league.or.jp/SFMS01/`

検索結果ページが素のHTMLで返ってくるので、そのまま取得して読めます。
1行が1試合で、次の11列があります。

```
シーズン / 大会 / 節 / 試合日 / K/O時刻 / ホーム / スコア / アウェイ / スタジアム / 入場者数 / 中継
```

URLの形は次のとおりです。

```
https://data.j-league.or.jp/SFMS01/search?competition_years=<年>&competition_frame_ids=<大会ID>
```

| 大会ID | 中身 | 使っているか |
|---|---|---|
| 1 | J1 | ✅ 学習データと2026-27の日程 |
| 2 | J2 | ✅ 昇格クラブの検証用 |
| 3 | J3 | — |
| 11 | ルヴァンカップ（ＹＬＣ） | ✅ 日程負荷の実測用 |
| 14 | スーパーカップ | — |
| 20 | J1昇格プレーオフ | — |

**天皇杯とACLはここにありません**（JFA・AFC主催のため）。
JFA公式サイトはJavaScriptで描画するので素のHTMLからは読めず、取得を諦めました。
これが唯一の取りこぼしですが、影響は小さいことを確認しています（後述）。

### 2026年から秋春制

シーズン欄の表記が `2025` から `2026/27` に変わりました。
`tools/parse.js` は先頭4桁を取って開始年（2026）を `s` に入れます。
そのため2027年3月の試合も `s = 2026` になります。

### 試合1件の形

```json
{
  "s": 2025,                  // シーズン開始年
  "seasonLabel": "2025",      // 公式サイトの表記（2026以降は "2026/27"）
  "comp": "Ｊ１",
  "round": 1,                 // 節。カップ戦など節を持たない大会は null
  "day": 1,                   // 「第1節第2日」の第2日
  "roundLabel": "第1節第1日",
  "date": "2025-02-14",       // 未定なら null
  "ko": "19:03",              // K/O時刻。未定なら null
  "h": "G大阪", "a": "C大阪",  // 半角に正規化したクラブ略称
  "hg": 2, "ag": 5,           // 得点。未実施なら null
  "venue": "パナスタ",
  "att": 34860                // 入場者数。無ければ null
}
```

クラブ名は公式サイトの略称を半角化したものです（`Ｃ大阪` → `C大阪`、`川崎Ｆ` → `川崎F`）。
アプリの `CLUBS` / `J1` 配列と一致します。

## 3. 作り直す手順

**いちばん簡単なのは1コマンドです。**

```bash
node tools/all.js            # キャッシュを使って全部やり直す（約60秒）
node tools/all.js --refetch  # 公式サイトから取り直す（数分・36リクエスト）
```

中で次の順に実行しています。個別にやり直しても構いません。

```bash
node tools/fetch.js       # 公式サイトから取得（raw/ にキャッシュ。--force で取り直し）
node tools/parse.js       # raw/*.html → *.json
node tools/tune.js        # パラメータを決める → params.json
node tools/build.js       # HTMLの埋め込みデータと定数を作り直す
node tools/verify.js      # 検算（79項目）。ここが全部通らないと完成ではない
```

`build.js` の後に、公開用ページ（`../publish/index.html`）も作り直す必要があります。
`all.js` はこれも実行します。個別にやるときは**必ず本体を引数に渡してください。**

```bash
cd ../publish && node build.js ../節別予想.html
```

引数を省くと**自分自身を元に組み直す**ので、古いモデルのまま残ります。
実際にそれで公開版だけ旧パラメータ（`H2H_K=24` / `CUR_W=1.5`）で放置されていたことがあり、
検算の7章はその取り残しを検出するために足したものです。

`build.js` は何度実行しても同じ結果になります（冪等）。
`--dry` を付けると差分だけ表示して書き込みません。

キャリブレーションの記録を作り直したいときは、`tune.js` の後に次を実行します。

```bash
node tools/calibrate-schedule.js   # 中N日の効果
node tools/calibrate-promoted.js   # 昇格クラブ（J2成績の持ち越し）
node tools/calibrate-venue.js      # 本拠地以外での開催・曜日
node tools/validate.js             # パラメータ選びが過剰適合していないかの詳細
```

### スクリプトの役割

| ファイル | 何をするか |
|---|---|
| `tools/fetch.js` | 取得だけ。解釈しない |
| `tools/parse.js` | 生HTML → JSON。取得はしない |
| `tools/lib/data.js` | JSONの読み込みと日付の扱い |
| `tools/lib/model.js` | **モデル本体**。バックテストもキャリブレーションもこれを呼ぶ |
| `tools/backtest.js` | 日付順のバックテスト。`run()` を他から使える |
| `tools/tune.js` | パラメータ決定 → `params.json` |
| `tools/validate.js` | 過剰適合の確認（1軸ずつ検証区間への影響を見る） |
| `tools/build.js` | `data/` → HTMLの定数 |
| `tools/verify.js` | 全検算（79項目）。**変更したら必ず通す** |
| `tools/all.js` | 上のスクリプトを順番に全部実行する（公開版の作り直しも含む） |
| `publish/build.js` | 本体＋アドオン → `publish/index.html`。**本体を引数に渡す** |
| `tools/calibrate-*.js` | 各項目の実測。結果は `data/calib-*.json` に残す |

## 4. 検算していること（`tools/verify.js`・全79項目）

「取れた」と「正しい」は別です。データ自身が満たすべき条件を書き出して機械に確かめさせます。

```
1. J1 2015-2025
   3588試合 / 各シーズンの試合数（306または380）/ 重複なし
   全試合に日付とスコアがある / 日付とシーズン年が矛盾しない
   20クラブ年は各クラブ ホーム19・アウェイ19
   平均得点 ホーム1.376・アウェイ1.212 / ホーム勝率40.7% / 引分率25.0%

2. 2026-27 の日程
   380試合 / 38節 / 各節10試合・20クラブが1回ずつ
   順序付き380通りが重複なく全部そろう / 各クラブ ホーム19・アウェイ19
   379/380に日付がある / 節が進むと日付も進む

3. ルヴァン杯・J2
   件数と日付の充足率 / 水戸・千葉のJ2成績が454試合ぶんある

4. パラメータと精度
   params.json に書いた log loss が再現する
   基準率・一様分布より良い / 日程補正は θ=0

5. アプリとの整合
   HTMLの埋め込みデータが j1-matches.json と1試合単位で完全一致
   HTMLの P・PROMOTED が params.json・promoted.json と一致
   FIXTURES_RAW が j1-2026.json と節・ホーム・アウェイまで完全一致

6. アプリのコードを Node で実行
   スクリプト全体が構文エラーなく解析できるか
   HTMLからモデル部分を切り出して動かし、確率の合計が1になるか
   ホームアドバンテージが効いているか / 380試合で期待得点が現実的な範囲か

7. 公開用ページ（publish/index.html）
   アドオンを剥がした中身が 節別予想.html と1文字単位で一致（＝本体に追いついている）
   埋め込まれたアドオンが publish/sync-addon.html と一致
   アドオンが借りている名前（FIXTURES / STATE / save / refit / renderAll）が本体にある
   個人情報らしき文字列が無い / 外部から読み込むリソースが0件
   アドオン込みで全スクリプトが構文エラーなし / パラメータが params.json と一致
```

## 5. 分かったこと（実測の結論）

詳しくは `../解説.md` を見てください。要点だけ。

| 項目 | 結論 |
|---|---|
| Wikipedia由来の旧データ | 3588試合中 **2件のスコアが誤り**。公式記録で修正した |
| 中N日・週中の別大会 | **効果を検出できない。** 補正を効かせるほど精度が落ちる → 入れない |
| 対戦相性（H2H） | **有害。** 弱めると学習・検証の両区間で改善した（`H2H_K` 24→80） |
| J2成績で昇格クラブを評価 | **採用できない。** 学習区間と検証区間で結論が逆になる（標本8クラブ） |
| 本拠地以外での開催 | ホーム有利が **強まる**（×1.04）。実測はできたがアプリには未適用 |
| 曜日 | 一貫した傾向は見えない |

### 天皇杯・ACLが無いことの影響

日程負荷を測るには「直前の公式戦がいつだったか」が必要です。天皇杯とACLが無いと、
本当は中3日なのに中6日と見えてしまう試合が混ざります。

手元にあるルヴァン杯を隠して測ると、この取りこぼしの規模が分かります。

```
リーグ戦だけで測ると 5190件のうち 719件（13.9%）で休養日数を過大に見積もる
```

1大会で約14%です。天皇杯とACLも同じ桁でしょう。
仮に本当の効果が -7%（従来アプリの想定）あるなら、1〜2割の混入では消えません。
実測では**符号すら逆向き**（休養が少ない側がわずかに良い）だったので、
「効果は無い」と判断できます。天皇杯・ACLを足しても結論は変わらないと考えています。
