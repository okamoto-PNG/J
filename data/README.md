# データ層（back）の説明

アプリ（`index.html` / `節別予想.html`）が使うデータは、すべてここから生成されています。
**HTML を直接手で書き換えないでください。** データを直したいときは、このディレクトリと
`tools/` を触って `node tools/build.js` を実行します。

---

## 1. 取得元

**Ｊリーグ公式データサイト** `https://data.j-league.or.jp/SFMS01/`

検索結果ページが素のHTMLで返ってくるので、そのまま取得して読めます。
1行が1試合で、次の11列があります。

```
シーズン / 大会 / 節 / 試合日 / K/O時刻 / ホーム / スコア / アウェイ / スタジアム / 入場者数 / 中継
```

URLの形は次のとおりです。

```
https://data.j-league.or.jp/SFMS01/search?competition_years=<年>&competition_frame_ids=<大会ID>
```

| 大会ID | 中身 | 使っているか |
|---|---|---|
| 1 | J1 | ✅ 学習データと2026-27の日程 |
| 2 | J2 | ✅ 学習データと2026-27の日程／J1昇格クラブの検証用 |
| 3 | J3 | ✅ **J2の新顔（J3から上がってきたクラブ）の評価用** |
| 11 | ルヴァンカップ（ＹＬＣ） | ✅ 日程負荷の実測用 |
| 14 | スーパーカップ | — |
| 20 | J1昇格プレーオフ | — |

**天皇杯とACLはここにありません**（JFA・AFC主催のため）。
JFA公式サイトはJavaScriptで描画するので素のHTMLからは読めず、取得を諦めました。
これが唯一の取りこぼしですが、影響は小さいことを確認しています（後述）。

### 2026年から秋春制

シーズン欄の表記が `2025` から `2026/27` に変わりました。
`tools/parse.js` は先頭4桁を取って開始年（2026）を `s` に入れます。
そのため2027年3月の試合も `s = 2026` になります。

### 試合1件の形

```json
{
  "s": 2025,                  // シーズン開始年
  "seasonLabel": "2025",      // 公式サイトの表記（2026以降は "2026/27"）
  "comp": "Ｊ１",
  "round": 1,                 // 節。カップ戦など節を持たない大会は null
  "day": 1,                   // 「第1節第2日」の第2日
  "roundLabel": "第1節第1日",

```

## 3. 作り直す手順

**ふだんは何もしなくてよくなりました。** 毎週タスクスケジューラが自動で見に行きます（3-b 節）。
手で回したいときは次のとおりです。

```bash
node tools/all.js            # キャッシュを使って全部やり直す（約60秒）
node tools/all.js --refetch  # 公式サイトから取り直す（数分・48リクエスト）
```

中で次の順に実行しています。個別にやり直しても構いません。

```bash
node tools/fetch.js               # 公式サイトから取得（raw/ にキャッシュ。--force で取り直し）
node tools/parse.js               # raw/*.html → *.json ＋ season.json（シーズン境界を導出）
node tools/tune.js                # J1のパラメータ（1周目・暫定）
node tools/calibrate-promoted.js  # J1昇格クラブの事前分布 → promoted.json
node tools/calibrate-j3.js        # J2の新顔を出自別に評価 → calib-j3.json
node tools/tune.js                # J1のパラメータ（2周目・確定）
node tools/tune-j2.js             # J2のパラメータ → params-j2.json
node tools/calibrate-schedule.js  # 中N日の効果
node tools/calibrate-venue.js     # 本拠地以外での開催・曜日
node tools/build.js               # HTMLの埋め込みデータと定数を作り直す
node tools/publish.js            # 公開ページ（publish/site/）
node tools/verify.js              # 検算（199項目）。ここが全部通らないと完成ではない
```

### 順番に意味があります

**パラメータと事前分布は互いを必要とします。**

```
tune.js          … 事前分布を使ってパラメータを決める
calibrate-*.js   … パラメータを使って事前分布を決める
```

そこで「暫定のパラメータで事前分布を決め → もう一度パラメータを測り直す」の**2周**にしています。
1周だけだと、`params.json` に記録した精度が、あとで書き換わった事前分布では再現しません。
**来季を模擬したときに検算の「精度が再現する」が落ちて、これが分かりました。**

`calibrate-j3.js` は `tune-j2.js` より前（J2のパラメータがその事前分布を使うため）、
かつ `tune.js` より後（J1の確定値を使って測るため）です。

`build.js` の後に、公開ページ（`publish/site/`）も作り直す必要があります。
`all.js` はこれも実行するので、ふだんは意識しなくてよいです。

```bash
node tools/publish.js
```

**以前は `publish/build.js` に引数を渡す形でした。** 引数を忘れると自分自身を元に
組み直してしまい、公開版だけ旧パラメータ（`H2H_K=24` / `CUR_W=1.5`）で放置される事故が
実際に起きました。いまは既定で本体を読むので引数は不要です。
検算の7章はその取り残しを検出するために足したもので、いまも残してあります。

`build.js` は何度実行しても同じ結果になります（冪等）。
`--dry` を付けると差分だけ表示して書き込みません。

キャリブレーションの記録を作り直したいときは、`tune.js` の後に次を実行します。

```bash
node tools/calibrate-schedule.js   # 中N日の効果
node tools/calibrate-promoted.js   # J1昇格クラブ（J2成績の持ち越し）
node tools/calibrate-j3.js         # J2の新顔（出自で2分割＋J3成績の持ち越し）
node tools/calibrate-venue.js      # 本拠地以外での開催・曜日
node tools/validate.js             # パラメータ選びが過剰適合していないかの詳細
```

## 3-b. 自動更新（毎週）

`tools/auto.js` を Windows のタスクスケジューラが**毎週月曜 12:00**に呼びます。

```
タスク名: J1予想アプリ 自動更新
記録:     data/auto-log.txt
```

やっていること。

```
1) 来季の日程が出たか、J1 を1本だけ見る
2) 出ていなければ、今季ぶん（4本）を取り直す
3) 中身が変わっていなければ何もしない
4) 変わっていたらパイプラインを回す
5) 検算が落ちたら、触る前の状態に全部戻す
```

**毎週48本取ると相手のサーバに失礼なので、ふだんは5本で済ませます。**
来季が現れたときだけ全年を取り直します（学習と予想の境界が動くため）。

### 中身が変わったかの判定は「パース結果」で見ます

生HTMLのハッシュで比べると、毎回変わる部分（セッションらしき値）のせいで
**中身が同じでも「変わった」と判定してしまいます**。実際それで毎週19ファイルを
書き換えて OneDrive を同期させていました。いまは日程・K/O時刻・結果だけを比べます。

### 失敗したときに中途半端な状態を残さない

無人で走るので、これが最重要です。実行前に生成物を**OSの一時領域**へ退避し、
検算が落ちたら全部戻します。`verify.js` の 6-d 章が「わざとファイルを壊して復元されるか」を
毎回確かめています。**効かない安全網は無いのと同じ**なので、そこは検算しています。

### 操作

```powershell
# いま何をするか見るだけ（何も書き換えない）
node tools/auto.js --dry

# すぐ走らせる
Start-ScheduledTask -TaskName "J1予想アプリ 自動更新"

# 状態と次回の予定
Get-ScheduledTaskInfo -TaskName "J1予想アプリ 自動更新"

# 記録を読む（UTF-8 なので -Encoding utf8 が必要）
Get-Content data\auto-log.txt -Encoding utf8 -Tail 20

# やめる
Unregister-ScheduledTask -TaskName "J1予想アプリ 自動更新" -Confirm:$false
```

**PC が起動していないと走りません。** 見逃した週は次に起動したときに埋め合わせる設定
（`-StartWhenAvailable`）にしてあります。PC が消えていても走らせたいなら
GitHub Actions などクラウド側に置く必要があり、いまの「ローカル完結」は崩れます。

## 3-c. クラウドで動かす（GitHub Actions）

PC の電源を落としていても走らせたいとき用です。`.github/workflows/auto-update.yml` が入っています。
**始め方は [クラウド化手順.md](../クラウド化手順.md) にまとめてあります。**

```
毎週月曜 03:00 UTC（＝12:00 JST）
  → node tools/auto.js
  → 変わっていたら生成物をコミット
  → publish/site/ を GitHub Pages に公開
```

判定・退避・復元は `tools/auto.js` が持っているので、**ワークフローは呼ぶだけ**です
（同じロジックを2箇所に置くと必ず片方が古くなります）。

### ★ローカルの自動更新は止めてください

**両方動かすと、生成物を2箇所で書き換えて必ず食い違います。**
クラウドに移したら、こちらを実行して Windows のタスクを消してください。

```powershell
powershell -ExecutionPolicy Bypass -File tools\setup-schedule.ps1 -Remove
```

以後、**リポジトリが正**になります。手元で見るときは `git pull` してください。

### なぜコミットが必要か

「Pages に出すだけでコミットしない」形も考えられますが、それだと状態が進みません。

- `data/season.json` が更新されないので、来季が公開された後も毎週「新シーズンが現れた」と判定し、
  **毎週48リクエストの全取得**をやり直してしまう
- `data/raw` のキャッシュが増えないので、取得が毎回やり直しになる

なので、検算を通ったものだけをコミットする形にしています。

### 公開ページは毎回作ります

`publish/` はリポジトリで追跡していないので、チェックアウトした時点では存在しません。
「変化なし」の週に作らないと成果物が無いまま Pages に進んで公開ページが壊れるため、
**データが変わっていなくても毎回 `tools/publish.js` を実行**します。
中身は追跡してある `節別予想.html` から作るので、毎回作っても同じ結果です。

### 動いているかの確認

```bash
node tools/check-cloud.js
```

実行履歴・自動コミット・公開ページの3つをまとめて見ます。
**「自動コミットが無い」＝失敗ではありません**（データが変わらなかった週は何もしないのが正しい）。
判断は実行履歴が緑かどうかで行ってください。

### 手で回す

Actions タブの「Run workflow」から `auto / force / rebuild / dry` を選べます。
`dry` は何も書き換えずに判定だけ見ます。

### 注意

- Runner は共有IPなので、公式サイトの 503 を踏みやすいかもしれません。
  取得できなかった年はキャッシュのまま進み、次週に拾います（`fetch.js`）。
- `data/raw` は48ファイル・16MB でリポジトリに入ります。毎季少し増えます。
- 依存パッケージは `tools/ai-yosou.js` だけが使うので、CI では `npm ci` しません。

### PC を変えたとき

**タスクスケジューラの登録はPCごとのもので、OneDrive では同期されません。**
新しいPCで1回だけ実行してください。

```powershell
powershell -ExecutionPolicy Bypass -File tools\setup-schedule.ps1
```

プロジェクトの場所はスクリプト自身の位置から、`node` の場所は PATH から解決するので、
**パスを書き換える必要はありません。** 実行すると先に `--dry` で動作確認し、それから登録します。

| 引き継がれるか | 中身 |
|---|---|
| ✅ 自動で付いてくる | `data/` `tools/` `publish/` アプリ本体（OneDrive が同期する） |
| ❌ 登録し直す | タスクスケジューラの登録 → 上のコマンド1回 |
| ❌ 手で移す | **ブラウザに入っている自分の予想・封印の salt・読み込んだ他の人の予想** |
| — 作り直される | `data/auto-log.txt`（記録なので消えても平気）、退避用の一時フォルダ |

**3行目が要注意です。** 予想は `localStorage` にあるのでPCが変わると消えます。
移る前にアプリの「データ」欄で**書き出し（JSON）**を押して文字列を保存し、
新しいPCで貼って「読み込み」してください。封印コードの照合に使う salt もこれに含まれます
（salt を失うと、チャットに貼った封印コードと照合できなくなります）。

新しいPCに Node.js が入っていない場合は、先に入れてください（このプロジェクトは
`tools/ai-yosou.js` 以外は依存パッケージなしで動きます）。

## 4. 検算していること（`tools/verify.js`・全199項目）

「取れた」と「正しい」は別です。データ自身が満たすべき条件を書き出して機械に確かめさせます。

```
0. シーズンの境界（season.json の自己整合）
   予想対象＝学習の終わり＋1 / 採点開始＝最初+3季 / 検証区間が消化済みの最後で終わる
   学習区間と検証区間が重ならない・空でない
   予想対象シーズンのファイルが実在し、古い年のファイルが残っていない
   締切の基準日が「最も早い試合日」で、負の日数が出ない

1. J1（学習データ・年は season.json 由来）
   件数が season.json の記録と一致 / シーズンが途切れていない
   各シーズンの試合数がクラブ数と整合する（n(n-1)/2 × 整数回）★表を直書きしない
   全試合に日付とスコアがある / 日付とシーズン年が矛盾しない
   どのシーズンも各クラブのホーム数＝アウェイ数
   平均得点 ホーム1.376・アウェイ1.212 / ホーム勝率40.7% / 引分率25.0%

2. 予想対象シーズンの日程（クラブ数・節数は season.json 由来）
   試合数・節数・1節の試合数・クラブ数が整合する
   順序付きの組み合わせが重複なくそろう / 各クラブ ホーム・アウェイ同数
   1試合を除いて日付がある / 節が進むと日付も進む

3. ルヴァン杯・J2・J3
   件数と日付の充足率 / 水戸・千葉のJ2成績が454試合ぶんある
   J3 が2015-2026の12シーズンそろう / 2015-2025は全試合にスコア・2026は未記入
   J3 は「試合日まで含めれば一意」（★同じ順序ペアが1回だけとは限らない。2015は3回総当たり）
   各シーズンの試合数がクラブ数と整合する（総当たりn回制で n が整数になる）
   2026-27 J2 の新顔の出自が J3 として特定でき、その J3 成績が存在する
   calib-j3.json の採否が採用規則（両区間で改善）と矛盾していない

4. パラメータと精度
   params.json に書いた log loss が再現する
   基準率・一様分布より良い / 日程補正は θ=0

5. アプリとの整合
   HTMLの埋め込みデータが j1-matches.json と1試合単位で完全一致
   HTMLの P・PROMOTED が params.json・promoted.json と一致
   FIXTURES_RAW が j1-2026.json と節・ホーム・アウェイまで完全一致
   promotedByClub が calib-j3.json と一致し、履歴なしクラブにだけ付いている
```

### J3 を足したら J2 の新顔の評価が良くなった

J2 の新顔には「J1 から落ちてきたクラブ」と「J3 から上がってきたクラブ」が混ざっています。
以前は J3 のデータが無く、両方を1組の平均像に寄せていました。実測すると別物でした。

```
出自      クラブ  試合   atkH     defH     atkA     defA
J1から      10    416   1.2156   0.8882   1.2353   0.8792   ← 強い
J3から      11    454   0.8482   1.2334   0.9352   1.1893   ← 弱い
混ぜた平均  21    870   1.0238   1.0684   1.0787   1.0410   ← 従来はこれ1組
```

新顔が絡む556試合で測った log loss（`node tools/calibrate-j3.js` で再現できます）：

```
                                   学習区間     検証区間
従来（混ぜた平均1組）               1.05645     1.07864
段階1：出自で2グループに分ける       1.04582     1.08287 → の後さらに改善
段階2：＋出身リーグの強さ×b=0.6      1.03840     1.07152   ← 採用
```

**21通り試した全設定が「両区間で改善」を満たしました。** J2→J1（採用できなかった）とは対照的です。
理由は標本の性質の違いでしょう。J1 の昇格クラブは 8クラブ・286試合しかなく、
学習区間と検証区間で傾向が逆になりました。J2 の新顔は 21クラブ・870試合あり、
しかも「J1から」と「J3から」の差が非常に大きい（atkH で 1.22 対 0.85）ので埋もれません。

**選び方には注意が必要でした。** 学習区間は `b` を上げるほど単調に良くなり続けるので、
`calibrate-promoted.js` と同じ「学習+検証の和」で選ぶと `b` が上がりきってしまいます。
検証区間は4つの見方すべてで `b=0.6` 付近が最良（内点最適）だったので、そちらで選んでいます。
理由はスクリプト内のコメントに書いてあります。

J2 全体（3532試合）への効果は log loss 1.06321 → **1.06127**、的中率 43.8% → **44.3%** です。

### J3 データの癖（2つ）

1. **同じ順序ペアがシーズン中1回とは限りません。** 2015年は13クラブしかなく、
   最大3回戦っています。J1・J2 で使っている一意性の検算をそのまま当てると落ちます。
2. **2015年に `J-22`（Jリーグ・アンダー22選抜）が36試合出ています。** 実クラブではなく昇格もしません。
   除外すべきか測ったところ、2026-27の新顔の事前分布への影響は最大 0.0017（`b` を掛けると約0.001）で、
   **無視できる水準**でした。そのため特別扱いはしていません。

### 天皇杯・ACLが無いことの影響

日程負荷を測るには「直前の公式戦がいつだったか」が必要です。天皇杯とACLが無いと、
本当は中3日なのに中6日と見えてしまう試合が混ざります。

手元にあるルヴァン杯を隠して測ると、この取りこぼしの規模が分かります。

```
リーグ戦だけで測ると 5190件のうち 719件（13.9%）で休養日数を過大に見積もる
```

1大会で約14%です。天皇杯とACLも同じ桁でしょう。
仮に本当の効果が -7%（従来アプリの想定）あるなら、1〜2割の混入では消えません。
実測では**符号すら逆向き**（休養が少ない側がわずかに良い）だったので、
「効果は無い」と判断できます。天皇杯・ACLを足しても結論は変わらないと考えています。
